The log is the feature, and four decisions behind it each have a wrong answer
that looks fine. History holds snapshots rather than patches, so `jumpTo` is an
index assignment that cannot drift from what a replay would produce. Trimming
shifts indexes, so `Transition.id` is monotonic and never reused — which is why
`reset()` keeps its own reference to the initial state and is not a synonym for
`jumpTo(0)`, since a full log no longer starts at `@@init`. Writing while
travelled truncates the redo tail. And `subscribe` is synchronous rather than an
`effect`, because effects coalesce: two writes in one tick would be reported
once, and a devtools log that silently drops actions is worse than none.

The bridge maps the monitor's action ids through its own `sentIds` array instead
of assuming they match history indexes; the two agree right up until the first
trim or reset, after which a naive `history()[actionId]` lands on a neighbour.
`IMPORT_STATE` and `ACTION` are refused with a reason in the monitor rather than
left unimplemented — both would mean widening arbitrary JSON into `T`, and there
is no runtime schema here to validate against.

`ThemeService` reaches the bridge through a dynamic `import()` behind an
`environment.production` guard, so it ships as its own lazy chunk in development
and esbuild drops it from production entirely. Both halves were checked against
the emitted output rather than assumed. Because that import resolves late, the
bridge replays existing history on connect.

## Phase 7 — Architecture & Patterns
- [x] SOLID audit of services with before/after refactors in `docs/solid.md` — five findings, five refactors (`THEME_PREFERENCE_STORE`, `AUTH_BYPASS_PATHS`, a substitutable `createMockAuthStore`, `PostReader`/`PostSearcher`/`PostWriter`, `TOAST_SCHEDULER`/`TOAST_ID_FACTORY`); three violations recorded and deliberately left to their own items (PR #25)
- [x] Facade pattern over NgRx Signal Store to keep components framework-agnostic — `AuthFacade` in `src/app/core/auth/` publishes four reads and four commands over `AuthStore`'s twenty members. What it takes away was all reachable before: `accessToken`/`refreshToken` as signals a template could interpolate, `updateTokens` pointing the same hazard the other way, the bootstrap and transport methods (`restoreSession`, `loadFromStorage`, `refreshAccessToken`, `loadCurrentUser`), and `rxMethod`'s `T | Signal<T> | Observable<T>` call signature and its returned subscription — `signIn(credentials): void` closes that last one. It passes the store's own signals through rather than wrapping them, with a spec asserting the identity so a `computed()` wrapper has to argue with a test. `core/` stays exempt (guards, `jwtInterceptor` and `app.config.ts` own the session lifecycle); `features/` and `shared/` are held to it by `no-restricted-imports`, checked against the failure it names on `@ngrx/*` and `@/app/store/**` including type-only imports. `createFakeAuthFacade` replaces three hand-rolled `useValue: any` store doubles with one the compiler checks, and two things it still cannot check have specs: that the class publishes nothing beyond its interface, and that the double's defaults describe a state the facade can reach. `isAdmin`/`userRole`/`hasRole` deliberately left off — every role decision happens in `roleGuard` before a component exists. 450 specs, up from 431 (PR #26)
- [x] Strategy pattern via multi-provider `InjectionToken` arrays — `API_ERROR_MAPPERS` in `src/app/core/http/errors/`, four `ApiErrorMapper` strategies (`offline`, `problem-json`, `message-envelope`, `string-body`) asked in order until one recognises the response. `errorInterceptor` now holds the list, not the logic, so a fifth backend format is one entry in `app.config.ts` and no change under `core/http`. Three behaviour changes fall out of it, each with a spec: a `text/plain` body is read rather than discarded, RFC 9457 problem+json is understood, and a status-0 `HttpErrorResponse` — DNS, CORS, offline — finally says "network error" instead of quoting Angular's status line. `ApiErrorMapper` carried a `priority` field until the spec written to justify it failed: a `multi: true` token resolves in the nearest injector that provides it and Angular does not merge the ancestors' contributions in, so a child injector *shadows* the parent's array rather than appending to it. Argument order to `provideApiErrorMappers` already orders the array, the field went, and the shadowing — which means a lazy route providing mappers replaces the set rather than adding to it — is pinned by a spec and written up in `docs/strategy-tokens.md`. 478 specs, up from 450 (PR #27)
- [x] Decorator pattern: `HttpInterceptorFn` composition for retry, cache, and telemetry — `composeInterceptors` folds interceptors into one (first argument outermost) and `interceptWhen` scopes the result, so `app.config.ts` applies the cache and the retry to this application's own API and nothing else. The fold runs each inner interceptor through `runInInjectionContext`, which Angular's own chain also does and which is not ceremony: `jwtInterceptor` calls `next()` from inside a `switchMap` while waiting on a token refresh, so a naive fold hands the interceptor beneath it NG0203 instead of a request — intermittently, only while a token happens to be expiring; a spec with a deliberately deferring interceptor pins it. The order *is* the design — telemetry outermost so it measures backoff and refresh queue, cache beneath `jwtInterceptor` so its key carries the `Authorization` header (above it, `/users/me` would be one slot shared by every identity the tab has held, and beneath it a sign-out needs no cache invalidation because the anonymous key simply does not match), retry innermost so three attempts are one cache entry and one telemetry span. What each decorator learned travels back up through a mutable `REQUEST_TRACE` on the `HttpContext`, the only object every layer shares. Three calls that could have gone the other way: nothing is cached unless the response carries `Cache-Control: max-age` or the call site names a `ttlMs` (guessing a TTL invents a freshness guarantee nobody made, and a stale page after a successful write reads as a bug in the write) — in-flight deduplication is on regardless, with `refCount: true` so cancellation still aborts; `POST`/`PATCH` are absent from the retry policy, there being no idempotency-key mechanism here to make resending a possibly-applied write safe; and `Retry-After` outranks the computed backoff unjittered but still clamped, so a misconfigured `Retry-After: 3600` cannot hang a request for an hour. Known limits written down rather than hidden: a cache hit emits no `HttpEventType.Sent`, `Vary` is unhonoured beyond `Authorization`, bodies are shared by reference, and `HTTP_CLOCK` is one wall clock because `Retry-After`'s date form needs one. No `ETag` revalidation, which is what would let `no-cache` be read as the RFC means it. 574 specs, up from 478; `docs/interceptor-decorators.md` (PR #28)
- [x] Dependency inversion with abstract-class provider tokens, swapped in tests — `PostReader`/`PostSearcher`/`PostWriter` become abstract classes, so the role is the *token* and not just the annotation. The finding the ISP item had left behind: `const posts: PostReader = inject(PostsService)` narrowed the type while the token stayed the concrete `HttpClient` wrapper, so the source arrow still ran from policy to detail — `core/routing/post-title.resolver.ts` imported a `features/` implementation to put a title in a tab, every double went in as `{ provide: PostsService, useValue: … }`, and `providedIn: 'root'` kept the implementation reachable regardless. `PostsService` → `HttpPostsService`, and `InMemoryPostsService` is a second real backend: a component spec now exercises the read-write cycle with no `HttpTestingController` configured at all. It is faithful where a caller can observe it — pagination, case-insensitive search, `AbortSignal` rejecting with exactly what `abortableRequest` produces, and a miss rejecting with the `ApiError`-shaped `{ status: 404, message }` `errorInterceptor` normalises a real 404 into rather than a bare `Error` that would let a spec pass against error handling the HTTP path would break; where it cannot be (no latency, so `search()` cannot demonstrate `switchMap` cancellation) is written down. `providePostsBackend` binds all three roles with `useExisting` and takes a `Type<PostsBackend>` — the one part of the wiring the compiler can check, since Angular types `useValue`/`useClass`/`useExisting` as `any`; the `useClass` hazard it avoids (three providers, three instances, a write `PostReader` cannot see) is a spec that reproduces the failure, not a comment. The providers sit on the lazy `DASHBOARD_ROUTES` rather than `app.config.ts`: the eager root cost +4.16 kB of initial bundle against a 565 kB budget with 5.63 kB of headroom, and raising the budget was rejected. 609 specs, up from 574; `docs/dependency-inversion.md` (PR #29)
- [x] Dynamic component rendering with `ViewContainerRef` and typed inputs — `dynamicComponent(Type, bind => [...])` in `src/app/shared/dynamic/` types each binding's name as `keyof` the component's `input()`/`model()`/`output()` declarations and its value as what that member accepts, closing the one hole the framework leaves open: `inputBinding`, `outputBinding`, `twoWayBinding`, `ComponentRef.setInput` and `NgComponentOutlet`'s `inputs` record all take a `string` name and an untyped value, so a rename or a typo compiles and then fails quietly. Three decisions the types forced: a transformed input maps to its *write* type, so `limit = input(5, { transform: numberAttribute })` accepts `string | number` here exactly as in a template; a `model()` is an input but not an output, because `ModelSignal<T>` extends both `InputSignal<T>` and `OutputRef<T>` and listing it naively would offer `collapsed` when the registered output is `collapsedChange` — a binding that typechecks and never fires; and the descriptor's component type is erased, because `type` needs `C` covariantly while `bindings` needs it contravariantly, so the erasure happens inside the factory after both ends have been checked against the same `C`. Two mistakes stay outside the type system — an aliased input, and an `@Input()` field, which is an ordinary property no `keyof` can distinguish — so `dynamicComponent` reflects the component once with the public `reflectComponentType()` and throws naming the input that was meant and the ones that exist, in production too. `DynamicOutletDirective` recreates on a change of the descriptor's *reference* and not otherwise, which is `createComponent`'s contract rather than a tuning choice: bindings are fixed at creation, so new bindings need a new view, and the payoff is that an unchanged descriptor keeps its component alive while the signals inside its bindings keep flowing in — a spec asserts the widget's DOM node is the same object after a range change. `WidgetBoardComponent` is the payoff and the argument for the shape: it renders whatever is registered under `DASHBOARD_WIDGETS`, imports no widget and knows no widget's inputs, because each definition binds its own component; a registry of `Type<unknown>` could not. Required inputs are still unenforceable (`input.required<T>()` and `input<T>()` are the same type), and host directives and `projectableNodes` are deliberately uncovered. 651 specs, up from 609; `docs/dynamic-components.md` (PR #30)
- [x] Standalone directive library: structural directive with a template type guard — `src/app/shared/directives/`, holding the two structural directives this application still needs now that `@if` and `@for` are language features. `ngTemplateContextGuard` is the item, and its value is what happens without it: a directive that omits one does not get `unknown` in its template, it types every `let-` variable `any`, silently, for every caller forever. Measured rather than asserted — `{{ data.titel }}` in `PostDetailComponent` fails `pnpm build` with TS2551 while the guard is there, and builds clean rendering nothing once the four lines are deleted. `*appAsync="post; let data; loading: skeleton; error: failed"` renders one of three branches of an `AsyncSnapshot<T>`, and the two adapters that build one are where each library's ordering hazard is handled once instead of in every template: `resource.value()` throws in the error state, which `PostDetailComponent` used to carry as a comment above a template whose branch order was the only thing keeping it true, and a failed TanStack refetch keeps the data it had, so `querySnapshot` reads `status()` before it looks for data rather than leaving a stale row under an unmentioned failure. `QueryLike<T>` is structural, three members, so nothing under `shared/` imports the query library — and it asks for `status` rather than the `isError` beside it because TanStack types its `is*` members as narrowing predicates whose `this` is the concrete query result, which is the dependency the indirection exists to avoid. The loaded view is updated in place rather than recreated, so a refetch that changes one field does not reset scroll, focus or a half-typed input; that needs `EmbeddedViewRef.markForCheck()`, since a context property is not a signal, and deleting the call turns a spec red. `*appRepeat="6"` covers what `@for` has no spelling for, replacing the `Array.from({ length: n })` fields both skeleton-drawing components carried; its context has one member, the index, because `$count` can only change when views are added or removed and keeping it in step would have needed a `markForCheck` no spec could make fail. `ngTemplateGuard_` — the form that narrows the bound expression — is absent from both and written up rather than faked: `@if (x; as y)` covers that case natively and neither binding has anything to narrow. So is any context on the `loading` and `error` templates, since Angular cannot type an `<ng-template>` passed as an input and publishing the error through one would hand back exactly the `any` the context guard removes. 681 specs, up from 651; initial bundle 560.36 kB against the unchanged 565 kB budget (+30 bytes — both callers are lazy routes); `docs/structural-directives.md` (PR #31)

- [x] Virtual scrolling with the CDK for a 10k-row table — `src/app/shared/virtual-table/` renders any number of rows with a screenful in the DOM; `/dashboard/activity` is the caller, 10,000 audit-log entries against about sixteen `role="row"` elements. - [x] Core Web Vitals instrumentation reported to an analytics sink — `src/app/core/vitals/` measures LCP, INP, CLS, FCP and TTFB during a real page load and hands them to a sink. Every other performance gate here prices the *artifact* on a build agent with a fast disk and no network; none of them can say that the dashboard's largest image takes four seconds to paint on a phone in a lift. FID is absent because it no longer exists — removed from the Core Web Vitals in March 2024, dropped from `web-vitals` in v5, and it scored a page perfectly whose first handler then blocked the main thread for a second. Measuring is the library rather than hand-rolled `PerformanceObserver`s: CLS's session windows, INP's per-page percentile, discarding a metric for a page hidden before it occurred and re-reporting after a bfcache restore are all things a re-derivation gets some subset of right and then quietly differs from Chrome's own field data on. It sits behind a dynamic `import()` — its own 8.80 kB chunk, not part of the initial bundle — and `provideWebVitals` registers from `afterNextRender`, so even the request for it is issued after the first paint. Not about the kilobytes: an analytics library downloaded *during* page load competes for bandwidth and main thread with the page whose load it is measuring, and `buffered: true` throughout the library means arriving late costs nothing except on a page abandoned in the first few hundred milliseconds, which now goes unreported — a bias written down rather than hidden. The part specific to a routed application is that a Core Web Vital belongs to a page *load* and not to a route, so every report carries two paths: `entryPath` from `DOCUMENT.location.pathname`, read in the app initializer because by first render `authGuard` may already have replaced `/dashboard` with `/login` and a load abandoned on the dashboard would be filed against the sign-in page, and `path` from `Router.url` when the metric settled — which differs only for INP and CLS, and there the difference is the point. And `web-vitals` reports its three late metrics from its own `visibilitychange` listener, so which of the two listeners runs first depends on when a lazy chunk finished loading — the beacon remembers that the page has been hidden and sends on arrival instead of assuming an order, with both orders asserted and the flag seeded from `document.visibilityState`. `WEB_VITALS_SINK` defaults to discarding, the call `HTTP_TELEMETRY_SINK` already makes; `vitalsUrl` is empty in both environments and the comparison is a build-time constant, so a build with no collector drops the beacon rather than shipping it unused. Turned on, it batches, flushes on `visibilitychange` and `pagehide` (a tab switch fires only the first, a bfcache-eligible navigation historically only the second), prefers `sendBeacon`, falls back to keepalive `fetch`, and sends JSON labelled `text/plain;charset=UTF-8` because that is CORS-safelisted and a preflight issued from `visibilitychange` is exactly the round trip an unloading document does not survive. No retry and no cross-page queue, deliberately. `app.config.spec.ts` stubs the subscriber: it bootstraps the real configuration many times over, and the real one registered observers and page-lifecycle listeners no `TestBed` teardown removes, which reported against Karma's own document as the suite ended and disconnected the browser. 860 specs, up from 808; initial bundle 563.09 kB → 565.02 kB against the unchanged 567 kB budget, every route budget untouched; `docs/web-vitals.md` (PR #36)

## Phase 9 — Forms & Accessibility
- [x] Typed reactive forms with a generic `FormGroup<T>` builder helper — `src/app/core/forms/` does not add typing to reactive forms, which have had it since v14; it reverses the *direction* of inference. `fb.group({ email: [''] })` returns a genuinely typed `FormGroup`, but the types flow from the spec to the form, so the form is whatever was written and agrees with itself by construction, and nothing compares it to the interface it exists to fill: a form missing a field, one carrying a misspelled extra, and one holding `string | null` where the payload wants `string` all compile, all render, and all pass every assertion a form spec normally contains. `typedGroup<T>()(spec)` makes the model an input — every field present, no extras, each control's value type exact — while the controls stay inferred, so `form.controls.email` is still a `FormControl<string>` and what comes back is an ordinary `FormGroup` with no wrapper; it is curried because TypeScript has no partial type-argument inference and pinning `TValue` in one call would mean writing out the spec type that is being inferred. `schemaGroup` derives fields, types and per-field validators from one Zod object schema and is what `/login` and `/register` now use; `nestedGroup` and `arrayOf` compose for what a flat schema cannot describe. Three findings, each pinned by a test rather than described in a comment. `nonNullable` is a statement about `reset()` and not a strictness preference: a control built without it resets to `null`, which is why `new FormControl('')` is honestly typed `FormControl<string | null>`, so a "clear the form" button writes `null` into a field the schema rejects with *Expected string, received null* in an input nobody touched — one spec asserts that against Angular directly, so the claim is checked and not repeated. `z.infer` is a schema's *output* type while a form holds its *input*: they coincide until a `.transform()` appears, at which point typing controls on the output means a `FormControl<number>` bound to a text input, so `schemaGroup` types the input side and `safeParse` at submit becomes a genuine conversion rather than the redundant re-validation it resembles. And a structural constraint cannot catch the one mistake the module exists to prevent: Angular's controls carry their value type through `setValue` and `patchValue`, which are *methods*, and methods compare bivariantly, so `FormControl<string | null>` satisfies a slot asking for `AbstractControl<unknown, string>` — `FieldSpec` therefore carries a never-called `rawValue: (raw: TRaw) => TRaw`, a function *property*, invariant under `strictFunctionTypes`, and deleting it makes `nullable-control.ts` compile. Because the product is types the tests are type tests: `expectTypeEquals` in `src/testing/types.ts` for the positive half, using the deferred-conditional identity trick rather than mutual assignability, which reports `any` as equal to everything; and `scripts/ci/fixtures/form-types/` for the negative half — ten files that are *supposed* to fail, each annotated with the diagnostic code and message phrase it must produce, since code that does not compile cannot live in a spec and `expect(form.getRawValue()).toEqual({ email: '' })` passes identically whether the return type is the model, a `Partial`, a nullable variant or `any`. `pnpm check:form-types` fails on an unannotated error as well as on a missing one, which `@ts-expect-error` cannot: it accepts *any* error on the line, so a fixture drifted into a typo would still satisfy it while testing nothing. Both failure paths were provoked against the real gate before it was trusted, and the matcher carries six self-tests because nothing under `scripts/` is in Karma's build graph. No lint rule bans `fb.group()` in new code — a non-nullable `FormControl` with no model to drift from is a legitimate answer, so the boundary is a judgement `docs/typed-forms.md` states rather than a rule a linter can hold. 940 specs, up from 912; initial bundle unchanged at 571.42 kB and every route budget untouched, with `/register` falling 111.88 kB → 108.22 kB of lazy JS — measured rather than assumed, since re-injecting a single `FormBuilder` puts 3.81 kB straight back as it and `NonNullableFormBuilder` stop tree-shaking out of the shared forms chunk; `docs/typed-forms.md` (PR #38)
- [x] Custom `ControlValueAccessor` component with full validation integration — a value accessor is told the value and nothing else: not that its control is invalid, not that it has been touched, not what the errors say, and not whether the rule it is failing is one it could have enforced itself. That is why `app-input` took an `error` string `@Input()` — a binding that type-checks while naming a *different* field's signal, that can be omitted entirely, and that a message arriving from anywhere but a template (`setErrors` from a server, an async validator settling) never reaches at all. `hostControl()` reads it off the control instead, so the message, `aria-invalid` and the border are one signal rather than three bindings maintained in parallel. Getting there is three findings, each pinned by a spec rather than described in a comment. Injecting `NgControl` in the constructor is NG0200 against the `NG_VALUE_ACCESSOR` the component provides on the same element, and the workaround everyone knows — drop the provider, assign `ngControl.valueAccessor = this` — breaks that cycle and does **not** extend to `NG_VALIDATORS`, which has no equivalent assignment, so a component wanting both ends up back at NG0200 by the second path; resolving the directive after construction keeps both declarative. `ngOnInit` is then the obvious hook and is wrong in exactly one of the two binding syntaxes: `FormControlDirective` takes its control as an `@Input` and has it before any hook, while `FormControlName` looks its up out of the parent `FormGroupDirective` in its own `ngOnChanges`, which runs *after* the hooks of the component sharing its element — so `ngControl.control` is `null` there, and a component built and specced against `[formControl]` renders no validation state at all under `formControlName`, which is most forms, with nothing failing anywhere. `writeValue` is the first moment both agree on and is still before the first render, so there is no second pass and nothing for a fixture's `checkNoChanges` to object to. `self: true` on the lookup is the third: the element-injector chain reaches ancestor elements, so a field rendered inside another accessor's template would otherwise bind to *that* control and report its errors under its own label. `TagInputComponent` is the component, and a tag editor because its text box is **not part of its value** — type a word, do not press Enter, submit, and the control holds `[]` while every outer validator agrees the field is fine and the visitor watches what they typed disappear; nothing above the component can see that text, which is what `NG_VALIDATORS` is for, so it is reported as `tagsPending` and the form will not submit. Committing on blur is the other answer and is worse: it turns a half-typed word someone was about to delete into a permanent tag, silently. `minTags`/`maxTags` are validators for the mirror reason — the component refuses to *add* past the ceiling but reports, never truncates, a value arriving through `writeValue` from a resolver or a server. `registerOnValidatorChange` is the hook nobody implements and the spec says why: Angular re-runs a validator when the *value* changes, so `maxTags` going 2 → 5 leaves the control red under a limit that no longer exists; the `untracked` around the callback is load-bearing, because it runs `updateValueAndValidity` synchronously into the component's own `validate` and without it every signal `validate` reads becomes a dependency of the effect that called it. Three of the four things that have to hold are consequences of how Angular runs async validators rather than of the rule itself, and each is pinned by a spec rather than described in a comment. **Debounce and cancellation are one mechanism.** There is no long-lived stream to hang `debounceTime` on — Angular calls an async validator afresh on every revalidation and subscribes to whatever comes back — so the delay is a `timer` *inside* the returned Observable, and that placement is the whole thing: `updateValueAndValidity()` unsubscribes the previous run before starting the next, and unsubscribing is what clears the pending timer and aborts an `HttpClient` request already in flight. A debounce applied anywhere outside is invisible to that and leaves superseded requests running into a form that has moved on; `async-cross-field.spec.ts` asserts the abort through `TestRequest.cancelled` against a real `HttpTestingController` rather than through a fake's own bookkeeping. **It goes on the field and not on the group**, though it reads two of them, because Angular runs a control's async validators only once its *synchronous* ones pass and a `FormGroup`'s synchronous validator is the whole form — on the group nothing would be sent until the name and both passwords were valid and matching, so the invite error would arrive last instead of beside the input that caused it; `control.parent` supplies the rest of the key. **The cost of moving it down is that Angular no longer knows the field depends on its sibling**, so a verdict outlives the email it was reached against: correct a typo and “issued to another address” stays on screen, and the form stays invalid, until the code itself is touched. `revalidateWhen` declares the dependency and refuses a source that is the target or one of its ancestors — revalidating a control updates its ancestors, whose `valueChanges` feed straight back in, and because each turn is scheduled rather than recursive that loop presents as a frozen tab rather than as a stack overflow, which is why it is a guard and not a note. **The memoisation is therefore not an optimisation**: declaring the dependency turns every keystroke in `email` into a revalidation of the code field, so without a cache the fix costs one request per keystroke in two fields instead of one. `keyOf` projects the control onto just what the check depends on, a settled key is answered synchronously so the control never re-enters `PENDING`, a `null` key means “not worth asking” (a blank optional field, or an email `registerBaseSchema` would reject), and the default `Object.is` comparison is documented as wrong for an object key — a composite key needs an `equal` or the cache never hits and the memoisation silently does nothing. A transport failure is deliberately never cached, and the default on a failed check is to **fail open**: a validator standing in front of a network that reports an error on a timeout has turned an availability blip into a lost sign-up without preventing anything the server was not going to reject anyway. `take(1)` lives inside the validator because a control stays `PENDING` until the Observable **completes**, not until it emits, and `status` is what `form.valid` and every disabled submit button read — `HttpClient` completes after one response, which is exactly why a missing one works against the real transport and hangs against anything that stays open, so the spec pins it with a `Subject` that emits and never completes.
