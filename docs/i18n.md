# Internationalisation

The application ships in two locales: `en-US`, which is the source, and `ar`, which is
Arabic — right to left, and with six plural categories where English has two. Both of
those are deliberate. One target locale is enough to prove that the pipeline works; a
target locale that only differed from English in vocabulary would have proved nothing
about either half of this document.

```
pnpm i18n:extract     # rewrite src/locale/messages.xlf from the source
pnpm start            # serve en-US, at /login, /dashboard, …
pnpm start:ar         # serve ar, right to left, same paths
pnpm build            # both locales, into dist/<app>/{browser,server}/<locale>/
pnpm check:i18n       # every string translatable, every translation current
pnpm check:rtl        # no physical-direction utilities
```

## Where the translation happens

Build time, not run time. `angular.json` names the locales, `localize: true` on the
production configuration builds each one, and `$localize` calls are replaced by their
translated text during that build. The alternative — shipping one bundle and calling
`loadTranslations()` at boot — costs every visitor the other locales' strings and puts a
parse on the critical path, and it does not survive server-side rendering: `$localize`'s
translation table is module state, so one Node process cannot serve two locales at once.

What that decision costs is the shape of the deployment, and it is the most visible
change in this repository:

**The application no longer has a root.** Every route lives under a locale prefix.
`/login` is `/en-US/login` and `/ar/login`; `/` is a redirect to the default locale's base
href, issued by `@angular/ssr`'s app engine. A reverse proxy in front of this is the right
place to pick a locale from `Accept-Language` and redirect accordingly;
`assert-ssr.mjs` asserts the 404 on the bare `/login` so that a deployment still pointing
traffic there finds out in CI rather than in production.

The development server serves one locale and does not prefix it, which is why `pnpm start`
is still `/login` and why every Playwright spec addresses the unprefixed path.

## Marking a string

Every string a user can read is marked, and `pnpm check:i18n` fails the build when one is
not — that gate exists because nothing else notices. `ng extract-i18n` collects what is
marked and says nothing about what is not, so an unmarked heading does not shrink the
catalogue, it never enters it. The build is green, every unit spec passes (they run
against the source locale, where an untranslated string is the correct output), and the
only place the omission exists is the Arabic page.

In a template:

```html
<h1 i18n="@@auth.login.heading">Welcome back</h1>
<button i18n-aria-label="@@ui.dialog.close" aria-label="Close dialog">…</button>
```

In TypeScript:

```ts
title: $localize`:Browser tab title and route announcement@@route.title.login:Login`;
```

Two rules about ids and descriptions, both enforced:

- **Every message carries an explicit `@@id`.** Without one Angular hashes the English
  text into an id, so correcting a typo orphans every translation of that message — and
  with `i18nMissingTranslation: "error"` the build then fails naming a hash rather than
  the string that moved.
- **A `$localize` description may not contain a colon.** `$localize` delimits metadata
  with `:`, so a colon inside the description ends the block early and the remainder
  becomes part of the message. This was live here for one commit:
  `` $localize`:Activity table column: who performed the action@@activity.col.actor:Actor` ``
  rendered as `who performed the action@@activity.col.actor:Actor` in the table header —
  in development only, because a localised build replaces the message by id. Escape it as
  `\:` or reword; `check:i18n` rejects metadata that does not reach an `@@`.

The explicit ids buy stability, and they have a cost that is the reason `check:i18n` reads
the translation files as well: **a reworded English string keeps its old translations.**
The id still matches, nothing is missing, and the Arabic build ships a sentence answering
the previous question. Comparing each translation's `<source>` against the catalogue's is
the only thing that sees it.

### What is not marked

Content, as opposed to chrome. A post's title arrives in whatever language it was written
in and is not ours to translate — `post-title.resolver.ts` says so on the line that
returns it, and the fallback beside it *is* marked. The same goes for the seeded posts and
activity rows, which stand in for an API.

The server's own error messages pass through untranslated too: they belong to the API,
which should localise them from the request's `Accept-Language`. What this application
supplies is the fallback for when the server says nothing useful, and those are marked.

## Plurals

**In a template, use an ICU `plural`.** The translator receives the whole construct and
declares the categories their language uses:

```html
<p i18n="@@dashboard.insights.postCount">
  {page.total, plural, =0 {No posts} =1 {1 post} other {{{ page.total }} posts}}
</p>
```

This replaced `{{ total }} post{{ total === 1 ? '' : 's' }}`, which is not a shorter way
of writing the same thing — it is English's own two-form rule compiled into the template,
where no translation file can reach it. Arabic selects between six categories, by value:
0, 1, 2, 3–10, 11–99, and everything else. `check:i18n` reads
`Intl.PluralRules('ar')` and fails a target that leaves one of them out, because Angular
does not: an ICU target with only `=1` and `other` compiles, and quietly applies the
`other` wording to 0, 2 and 3.

**In TypeScript there is no ICU**, because `$localize` does not parse one. `core/i18n/`
supplies `selectPlural`, which asks `Intl.PluralRules` and takes a message for *every*
category — the type demands all six. English then repeats itself five times, which looks
tiresome and is the honest price: a `$localize` message is chosen at build time by id, a
plural category at run time by value, so the source has to declare a message with the id
that the Arabic `few` will be looked up under. A translator cannot add one. The partial
record with an `other` fallback is the version of this that compiles, reads as tolerant,
and silently hands Arabic the wrong form five times out of six.

The practical rule that falls out: **if there is a template, put the plural in it.**
`activity-log.component.ts` moved its count out of the class for exactly this reason.
`tag-input.component.ts` and `post-typeahead.component.ts` could not — one produces a
validation message, the other a live-region announcement — and they are what
`selectPlural` exists for.

## Numbers and dates

A localised build does not localise `Intl` for you. Three `new Intl.NumberFormat('en-US')`
calls in `stat-widget.component.ts` and one `toLocaleString('en-GB')` in the activity log
were hard-coded, which is the failure mode a translated page does not announce: every
string arrives in Arabic and the numbers beside them stay in Latin digits with an English
separator. They read `LOCALE_ID` now, which in the Arabic build means Eastern Arabic
numerals.

`new Intl.PluralRules()` with no locale has the same problem and a worse symptom: it asks
the *browser* what language it is in, which is a fact about the visitor's machine rather
than about the bundle they were served.

Not everything locale-shaped should follow the locale. The activity log's timestamps stay
`en-GB` and UTC on purpose — it is an audit trail, and two people reading the same row in
different time zones disagreeing about when it happened is a support ticket. The comment
on `OCCURRED_AT_FORMAT` is the decision; this is the note that it was one.

## The right-to-left pass

`dir="rtl"` on `<html>` arrives for free: Angular writes `lang` and `dir` from the locale,
with nothing in `src/` involved. It is also, on its own, close to worthless.

`dir` moves the **inline axis** — text direction, `margin-inline-start`, `flex-direction:
row`, and every `ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-` utility. It does not move anything
written physically. `ml-4` is `margin-left` in both directions, `left-0` is the left edge
in both, `border-r` is the right border in both. So a layout built on physical properties
does not break loudly when mirrored — it reflows into a consistent, plausible-looking,
wrong version of itself, and nothing fails: not the compiler, not ESLint, not the unit
suite (which asserts behaviour), and not the axe audit (which reads the accessibility
tree, where "left" is not a concept).

`pnpm check:rtl` bans the physical utilities and names the logical replacement.
`e2e/a11y/rtl.spec.ts` is the other half, measuring the rendered result for the two places
where the fix is not a class-name swap:

- **Transforms have no logical form.** `-translate-x-full` moves the closed drawer left
  whatever `dir` says, and under RTL the drawer is anchored to the *right* edge — so it
  slides across the page rather than off it, covering the content while remaining `inert`
  and invisible to every other gate. The fix is Tailwind's `rtl:` variant, which compiles
  to `:where([dir="rtl"] &)` and so follows the same attribute the logical utilities do.
- **Variant order decides the winner.** `rtl:translate-x-full` is emitted after
  `md:translate-x-0`, and both are one class of specificity, so the first attempt at that
  fix pushed the *desktop* sidebar off the right-hand edge of every Arabic page. Scoping
  the closed state to `max-md:` says what was always meant: the panel only slides where it
  is a drawer. The e2e spec caught it; the source-level gate could not have.

The e2e pass sets `dir` on the running development server rather than serving the Arabic
build, and that is faithful for what it measures: the compiled CSS is one file for every
locale, and both logical properties and `rtl:` variants resolve against the attribute at
runtime. What it does not cover is the text, which is covered where it can be —
`check:i18n` against the catalogue, `assert-ssr.mjs` against the prerendered Arabic bytes.
`pnpm start:ar` serves the real thing for a manual pass.

## Hydration

`provideClientHydration(withEventReplay(), withI18nSupport())`. The second feature is not
an optimisation: without it Angular marks any component whose template contains an `i18n`
region `ngSkipHydration`, throws away the server's markup for that component and renders
it again.

On most pages the cost is the wasted work. On `/login` it was the feature: a component
that skips hydration takes every `@defer (hydrate …)` block under it with it, so marking
that page's heading translatable silently switched incremental hydration off and put the
101.89 kB of `@angular/forms` and Zod that the block exists to postpone back on the load
path. Nothing reported it — no compiler diagnostic, no runtime warning, no failing unit
spec — and the rendered page differed only in three attributes: `ngb`, `jsaction`, and
the event-dispatch contract script. `assert-ssr.mjs` reads those out of the prerendered
bytes, which is how it was found; the axe suite's "login form showing validation errors"
case failed at the same time, because the form it types into was never hydrated.

## What the gates cover, and what they do not

| Question | Answered by |
| --- | --- |
| Is every user-visible string translatable? | `pnpm check:i18n` |
| Does every message have a stable id? | `pnpm check:i18n` |
| Is every translation current, complete and non-empty? | `pnpm check:i18n` |
| Does each ICU declare the categories its locale uses? | `pnpm check:i18n` |
| Is the layout written in logical properties? | `pnpm check:rtl` |
| Does the mirrored layout hold up? | `pnpm e2e:a11y` (`rtl.spec.ts`) |
| Did the translation reach the artifact? | `pnpm check:ssr` |
| Do `lang` and `dir` reach the markup? | `pnpm check:ssr` |
| Is a message missing at build time? | `i18nMissingTranslation: "error"` |

Three gaps, recorded rather than closed:

- **The Arabic is machine-produced and has not been reviewed by a native speaker.** The
  structure is checked — placeholders, plural categories, ids — and the wording is not.
- **`ng extract-i18n` reads the build graph**, so a component nothing imports contributes
  no messages. `TagInputComponent` and `DialogComponent` are marked up and absent from the
  catalogue for that reason; the first route that renders one fails the build under
  `i18nMissingTranslation`, which is the loud version of this problem but still a
  surprise.
- **`src/locale/messages.xlf` is a committed snapshot.** `check:i18n` compares the
  translations against it, not against a fresh extraction — that would cost a build per
  run. `pnpm i18n:extract` is what keeps it honest, and a message added without running it
  fails at build time instead.
